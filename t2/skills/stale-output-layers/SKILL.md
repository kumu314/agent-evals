# 改了没生效：分层定位，别乱敲重启

"改了却看不到"的几乎唯一解释：**你的改动落在某一层，而你眼睛盯的是另一层**。
正确动作不是"再改一次"或"全部重启"，是**逐层拿读数，找出哪两层的内容不一致**。

## 1. 先背下这张层表

一次改动从落盘到被看见，通常要穿过五层，每层都有自己的"旧内容驻留方式"：

| 层 | 旧内容从哪来 | 拿到"这层是新是旧"的读数 |
|---|---|---|
| ① 源码/数据 | 你以为改的文件，可能不是真正被加载的那份 | 对**被加载路径**上的文件算哈希、看 mtime |
| ② 构建产物 | 源码变了，产物没重新生成 | 产物 mtime 是否早于源码 mtime |
| ③ 常驻进程 | 进程在改动之前启动，内存里还是旧代码 | 进程启动时间 vs 文件 mtime，谁先谁后 |
| ④ 浏览器/渲染 | Service Worker、强缓存把旧页面喂给你 | 响应头的缓存标记、产物 URL 上的指纹串 |
| ⑤ 部署副本 | 你验的是本机，用户看的是远端另一份 | 远端资源的哈希与本机产物比对 |

关键认识：**这五层的缓存互不连通**。重启进程只解决③，硬刷新只解决④，
重新构建只解决②——猜错层时，所有动作都是白做，还会把现场证据破坏掉。

## 2. 定位纪律：从离"眼睛"最近的一层往回查

1. **先确认你看的确实是产物**：在产物里塞一个唯一的标记串（改一个标题字），
   刷新后看不到 → 你看的根本不是这份产物，问题在④/⑤，不在①②③。
2. **比对相邻两层的内容**，而不是比"印象"：产物里搜不到源码新增的串
   → 卡在②（没构建）或构建吃的是另一份输入；产物里有、页面上没有 → 卡在③/④。
3. **进程类**：把"进程启动时间"和"文件 mtime"摆在一起比。启动早于改动，
   这个进程就永远不可能体现改动——这不是缓存问题，是身份问题，清任何缓存都没用。
4. **只有排除完才谈"清缓存"**，且每清一层立刻验证一次，不要三连击后再看结果——
   那样即使好了，也不知道是哪一层起的作用，下次复发照样不会修。

## 3. 反模式清单

- 「重启一下试试」当作第一步：破坏现场，把"哪一层坏了"的证据也重启掉了。
- 用"我确实改了"当证据：你改的可能是构建目录里的旧副本、另一个工作树、
  或编辑器里没保存的缓冲——**先证明改动落在被加载的那份文件上**（读回、算哈希）。
- 把浏览器硬刷新当万能药：Service Worker 不受它指挥，要走 SW 注销/跳过缓存开关。

## 4. 一句话判据

修"改了没生效"的验收标准不是"能看到了"，是**说得出改动穿过了哪几层、
每层当场取了什么读数证明它是新的**——讲不出层的"好了"，是下一次复发的起点。
