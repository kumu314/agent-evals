# push 卡住了：客户端的沉默不等于没推上去

`git push` 终端卡了三分钟没有任何输出，你按下 Ctrl-C。直觉：「肯定没推上去，重来一次」。
**这个直觉常常错**——而且"重来一次"在别的场景（比如已经写成功的提交）可能制造重复副作用。

## 1. 为什么"看着没成"其实可能成了

- push 分两段：**客户端把数据传出去** → **服务端接收并更新 ref**。网络在第二段慢，
  你会看到客户端一直挂着等一个回显，但**数据可能早就到服务端、ref 可能已经动了**。
- 客户端超时/被中断，丢的是**那条回执**，不一定是**那次写入**。退出码 124（超时）、
  空输出、`Everything up-to-date`，都只描述客户端当时的视角，不描述服务端真实状态。

## 2. 唯一可信的是"远端独立读数"

判成没成，去问服务端，不要问刚才那个客户端：

```bash
git ls-remote origin main        # 远端 main 现在指向哪个 sha
git rev-parse HEAD               # 本地要推的 sha
```

- 两者**相等** → 已经推上去了，那句 up-to-date 是**真的**（因为确实成了），不要再推。
- 两者**不等** → 这次确实没成，可安全重试（远端没动，不存在重复问题）。
- 关键：`Everything up-to-date` 既可能是"其实早推成了"也可能是"什么都没做"，
  **它本身不携带"远端等于哪个 sha"的信息**，必须靠 ls-remote 的绝对读数定性，而不是靠这句话。

## 3. 中断后的正确动作（顺序）

1. **先复核，别急着重推**：跑上面两条对比 sha。这是零副作用的只读操作。
2. sha 一致 → 收工。sha 不一致 → 再推（此时重推安全，因为远端没变）。
3. 反复不一致且报网络错 → 那是连接层问题（代理/被封），换传输通道，而不是无限重试。

## 4. 推广到所有网络写操作

同一套判据适用于任何"发出后想知道成没成"的写：API 建资源、发通知、提交任务——
**别拿发送端的返回当"成功"，拿目标端的查询回读当"成功"**。
返回值只证明"我这边跑完了"，回读才证明"那边真变了"。

## 5. 一句话判据

问"推上去没有"，答案只能来自 `ls-remote` 读到的远端 sha 与本地 HEAD **相不相等**这个外部读数；
客户端的超时、空输出、up-to-date 那句话，全都不是判据。
