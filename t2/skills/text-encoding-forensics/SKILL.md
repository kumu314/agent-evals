# 哈希对不上、却"看着完全相同"：先看不可见字节

同一份配置，Windows 上算的 sha256 和 CI（Linux）上算的不同，肉眼逐字比对"一模一样"。
直觉反应是「文件被改坏了 / 有人动了内容」——**多数时候错**。内容没变，变的是字节层。

## 1. 三类肉眼看不见的元凶

| 现象 | 真身 | 怎么在字节层认出它 |
|---|---|---|
| 文件首多出 3 个字节 | UTF-8 **BOM**：`EF BB BF`（Windows 记事本/"带 BOM 的 UTF-8"会加） | `xxd file \| head -1`，看开头是不是 `efbb bf` |
| 每行末尾差 1 字节 | 行尾符：Windows `CRLF`(`0d 0a`) vs Unix `LF`(`0a`) | 数 `\r`：`grep -c $'\r' file`，非 0 就是混了 CRLF |
| 中文变乱码/问号 | 编码不同：GBK / latin-1 被当 UTF-8 读（或反之） | `file -i file` 看探测编码；`xxd` 看高位字节范围 |

哈希是对**全部字节**求的，这三个都在字节里，只是眼睛看不见——所以"看着相同却不同"完全自洽。

## 2. 取证顺序（别一上来怀疑内容）

1. **先做字节比对，不做文本比对**：`cmp fileA fileB` 直接指出第一个不同的字节**偏移**，
   再看那个偏移落在首字节（BOM）、还是每行末（CRLF）、还是正文（真内容）。
2. **文本 diff 会骗你**：很多 diff/编辑工具默认忽略行尾与 BOM，于是"diff 无差异、哈希却不同"——
   这个矛盾本身就是线索：问题在它们忽略的那层（不可见字节），不在正文。
3. **确认归因后再修**：是 BOM 就去 BOM（存成"UTF-8 无 BOM"）、是 CRLF 就统一行尾
   （`.gitattributes` 的 `text=auto` / `eol=lf`）、是编码就显式指定读法。**不要改内容去"凑哈希"。**

## 3. 反模式

- 「肯定是被谁改了」——不先看字节就下结论，往往是 BOM/行尾，改内容南辕北辙。
- 用文本 diff 判"两文件相同"，再拿哈希对不上当灵异事件——两者用了不同的比较口径，矛盾是必然的。
- 手动重敲"看起来一样"的内容想让哈希相等——只要行尾/BOM 还在，永远不相等。

## 4. 一句话判据

"内容看着一样、哈希不一样"时，第一个要回答的不是"谁改了内容"，而是
**"首字节是不是 BOM、行尾是不是 CRLF、编码是不是 UTF-8"这三样**——`xxd`/`cmp` 十秒就能证实，
在它们被排除之前，任何"内容被改"的结论都为时过早。
