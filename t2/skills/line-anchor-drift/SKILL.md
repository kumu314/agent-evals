# 行号是不稳定锚：报告里的位置怎么才不会失效

一个反复出现的场景：上一轮报告写「`x.js:88` 有问题」，这一轮别人在文件顶部加了两行 import，
你去跳第 88 行，发现根本不是那句。对方说「第 88 行没问题，你写错了」。**你们都没记错——行号本来就会漂。**

## 1. 为什么会漂（机制，不是谁的锅）

- 行号是对"文件当前第 N 个换行符"的**位置引用**，不是对"某段内容"的**身份引用**。
- 只要在引用点**之前**插入或删除任何行，后面的行号全部平移。这是设计使然，与内容对错无关。
- 所以：**把 `88` 改成 `90` 是治标**——下一次任何人在前面加一行，`90` 又错了。你只是把同一个会复发的隐患往后推。

## 2. 正确修法：把位置锚换成内容锚

判据不是"这文件第几行"，而是"**能被逐字命中的那段原文**"。可复现的三条：

1. **引用带原文片段**：报告里除了结论，附上被指语句的一小段可 grep 的字面串
   （`if (arr[i] > len)` 这种唯一性足够高的），行号只当"当前快照的便利跳转"，明确标注会漂。
2. **交付前逐字命中一遍**：对每一条引用，`grep -F '<那段原文>' <file>` 必须命中；
   命不中说明内容真的变了（不是行号漂移），得回去核对，而不是改行号。
3. **区分两种失败**：
   - 文本还在、只是行号变了 → 换轨（用锚重算新行号），内容结论不变。
   - 文本也搜不到了 → 引用过期，**结论可能已失效**，必须重新核对再更新，不能只换个数字。

## 3. 反模式

- 「我记得是 88 行」——凭印象报行号，且不给内容锚，下一轮必然对不上。
- 行号找不到就断言「对方写错了」——大概率只是漂移，先 grep 原文再下结论。
- 把整份报告的行号列手动 +2 修正——下次又漂，白做。

## 4. 一句话判据

一条位置引用"活得好不好"，判据不是行号对不对，而是：**附的那段原文此刻还能不能在文件里逐字命中**。
命中得了，行号错了也只是跳转偏一下；命中不了，说明要改的是结论，不是数字。
